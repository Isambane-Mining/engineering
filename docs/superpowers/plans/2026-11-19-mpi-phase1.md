# MPI Fleet Activity Phase 1 implementation and LAB review

Goal: manually synchronize the latest MPI vehicle activity by IMEI, with reviewable Asset mappings.

Architecture: API MPI Settings is a singleton with API Configuration and Vehicle Mapping tabs;
MPI Vehicle Mapping is its child table; MPI Results contains one latest record per IMEI.
Only new MPI files are added. WearCheck, hooks, workspace navigation and existing changes stay untouched.

Implementation plan:
- Add focused, offline regression tests for matching, payload filtering and request handling. Do not run them in this session.
- Add the three DocTypes and manual Sync Now form action.
- Add an MPI controller with a permission-checked enqueue entry point, deduplicated job and worker lock.
- Discover up to 500 vehicles, process status requests in batches of 10 with at most 5 concurrent requests,
  with connect/read timeouts of 5/20 seconds and no retries. Commit each result independently.
- Preserve existing Asset links. Auto-link only a unique raw identifier match across Asset.name/asset_name;
  normalized comparisons produce suggestions only. Keep ambiguous and unmatched rows.
- Inspect the final files and Git status; verify pre-existing changed-file hashes. No test, migration,
  build, restart, commit, stash, reset or push commands are executed.

Design decisions:
- Settings are writable by System Manager and Engineering Manager; results are read-only to Engineering/Fleet roles.
- Enabled defaults to off. Password uses Frappe encrypted Password storage and is retrieved only in the worker.
- Use the user-verified POST object list and Basic Auth GET status endpoints. Require the exact HTTPS MPI origin;
  reject redirects so credentials cannot be forwarded to another host. Do not persist raw payloads or remote errors.
- A failed vehicle retains its prior result. Partial success records Last Error and leaves Last Success unchanged.
- Reject incomplete status snapshots (any missing numeric activity field or position timestamp), preserving
  prior results, because Frappe would coerce missing numeric values to false zeroes. Zone may be blank.
  An older position cannot overwrite a newer one. No activity is inferred from unrelated fields.
- `moving` preserves the API numeric duration in seconds; parking duration is seconds. Unix position timestamps
  are converted from UTC to the Frappe site's timezone. Zone is accepted only as an explicit scalar zone field.
- Mapping edits also update the Asset reference on an existing MPI Result without another API request.
- No scheduled polling, deletion of absent vehicles, driver/contact/VIN/sensor/configuration storage or item matching.

API references used to confirm payload structure (the user-verified MPI endpoints remain authoritative):
- https://docs.pilot-gps.com/list_of_objects.html
- https://docs.pilot-gps.com/7.7/vehicle_status_print.html
